## What has been completed

The new Climate App has been designed and implemented as a compact Home Assistant App using the old PostgreSQL Climate 5 repository only as a **behavioral reference**.

The PostgreSQL architecture itself was deliberately not ported.

Removed from the new design:

- PostgreSQL as business engine;
- SQL jobs and handlers;
- Matrix subsystem;
- Firewall subsystem;
- Dispatcher;
- UC queue;
- Universal Controller lifecycle;
- Confirmator lifecycle;
- PostgreSQL runtime/session machinery.

Replacement architecture:

```text
Home Assistant states
        ↓
Python Climate Core
 ├─ Outdoor / avg24 / season
 ├─ Room thermostat
 ├─ Humidity
 ├─ FAST/SLOW policy
 └─ Safety predicates
        ↓
Desired physical state
        ↓
Home Assistant services

Climate Core
        ↓
MQTT Discovery
        ↓
Home Assistant UI
```

## Implemented product behavior

### Outdoor / season

- ordered priority/fallback outdoor temperature sources;
- ordered priority/fallback outdoor humidity sources;
- temperature and humidity priorities are independent;
- time-weighted rolling 24-hour outdoor average;
- rolling history persisted in SQLite;
- live outdoor temperature loss forces season OFF;
- global season states:
  - `heat`
  - `cool`
  - `off`;
- season formula retains the Climate 5 thresholds/hysteresis semantics;
- one global house-wide temperature hysteresis is used by current product decision;
- MQTT two-threshold `heat_cool` facade:
  - low target = heating season threshold;
  - high target = cooling season threshold;
  - current temperature = avg24;
  - action = heating/cooling/idle;
- threshold changes persist across restart.

### Rooms

- one configured room = one MQTT Device;
- each room can therefore be assigned to a Home Assistant Area;
- one main `climate` entity per room;
- room temperature = average of currently valid configured room temperature sensors;
- room humidity = average of currently valid configured humidity sensors;
- profiles:
  - day
  - night
  - away
  - antifreeze;
- profile precedence retained from legacy Climate 5;
- room target matrix persisted by room × season × profile;
- temporary profile-edit overlay retained from legacy facade behavior;
- room HVAC mode is constrained by global season;
- stateful symmetric hysteresis;
- previous action persisted so restart does not collapse hysteresis state.

### FAST devices

Supported physical domains:

- `switch`;
- `climate`.

FAST devices follow room thermostat demand.

For `climate` actuators the App drives HVAC mode and room target.

For `switch` actuators the App drives on/off.

Execution is idempotent: commands are sent only when desired state differs from actual HA state.

### SLOW devices

The first implementation supports SLOW heating through local physical `climate` thermostats only.

Typical use case: floor/slab thermostat with its own local probe.

Behavior:

```text
HEAT season -> climate heat + slow_target
COOL/OFF    -> climate off
```

SLOW does not cycle from room-air thermostat demand.

The physical thermostat remains the local final control/safety loop.

A plain SLOW switch is rejected in v0.1 because continuous seasonal ON is not generically safe.

### Humidity

Optional per room:

- humidifier;
- dehumidifier.

Exposed using native MQTT `humidifier` facade.

Includes:

- current humidity;
- persisted target;
- independent humidity hysteresis;
- direct switch/humidifier actuator execution.

### Window context

Legacy room-window semantics were restored:

```text
any open contact            -> open
none open + one unavailable -> unknown
otherwise                   -> closed
```

Window state is context, not thermostat truth.

Only devices explicitly listed in `window_off_devices` are forced off while a configured room window is open.

Unknown configured window state is exposed as a warning Problem.

### Cold-weather reversible climate protection

Legacy Climate 5 had `ac_min_outdoor_temperature` with default `-10 °C`.

The new App maps this behavior to reversible FAST `climate` entities configured in both heat and cool lists.

During heating:

```text
current outdoor temperature < ac_min_outdoor_temperature
-> reversible climate device held OFF
```

Other eligible heating devices remain independent.

## Persistence

SQLite path:

```text
/data/dh_climate.db
```

It stores only restart-persistent state:

- season thresholds;
- rolling outdoor samples;
- room target matrix;
- room climate control state;
- previous room thermostat action;
- humidity targets/control state.

SQLite is not used as an orchestration engine.

## HA connectivity

Implemented:

- Supervisor REST API;
- HA WebSocket state subscription;
- subscribe-before-snapshot reconnect flow;
- timestamp-protected state cache;
- old buffered events cannot overwrite newer snapshot truth;
- cached HA truth is discarded on disconnect;
- physical commands are not sent without live HA connection.

## Telemetry

Implemented opt-in DigitalHouses Telemetry Protocol v1 support.

Properties:

- default disabled;
- persistent anonymous installation UUID/token;
- daily heartbeat with deterministic jitter;
- version-change heartbeat eligibility;
- one-hour failure backoff;
- telemetry failures do not affect climate runtime;
- authenticated installation deletion;
- payload does not contain room/entity/device/climate data.
